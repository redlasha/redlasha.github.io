# 실측

이 블로그의 차별점은 **관찰 기반**이라는 것이다. 공식 문서 두 문장을 겹쳐 추론한 것과 직접 돌려본 것은 근거의 급이 다르다. 실측은 여기에 프로토콜과 결과를 함께 남긴다.

## 규칙

- **가설과 반증 조건을 먼저 쓴다.** 결과를 보고 가설을 맞추지 않는다
- **대조군을 둔다.** "캐시가 안 잡혔다"는 격리 때문일 수도, 실험 자체가 잘못됐기 때문일 수도 있다
- **결과가 가설을 반증하면 그대로 기록한다.** 반증된 실험이 가장 값비싼 자산이다
- 측정값은 원본 그대로 적는다. 반올림하거나 요약하지 않는다

## 실험 1 — 계정 간 캐시 격리

상태: **미실행** (3편의 선행 작업)

### 가설

계정(조직)이 다르면 같은 디렉터리·같은 모델·같은 prefix여도 프롬프트 캐시를 공유하지 않는다.

근거: 공식 문서의 두 문장.
- "Caches are isolated between organizations"
- "Sessions you run in parallel in the same directory build matching prefixes and read each other's cache"

### 반증 조건

**3단계에서 `cache_read_input_tokens > 0`이 나오면 가설 기각.** 이 경우 3편의 핵심 논지("계정으로 쪼개면 캐시 공유를 잃는다")가 성립하지 않으므로 글 전체를 다시 설계해야 한다.

### 통제 변수

아래가 하나라도 다르면 캐시 미스가 계정 때문인지 알 수 없다.

| 변수 | 맞출 것 |
|---|---|
| 작업 디렉터리 | 동일 (worktree도 동일) |
| 모델 | 동일 |
| effort | 동일 |
| Claude Code 버전 | 동일 (중간에 업그레이드 금지) |
| git 상태 | 동일 (커밋·브랜치 변경 금지 — 순차 세션은 git 스냅샷이 같아야 캐시를 탄다) |
| CLAUDE.md | 동일 (수정 금지) |
| MCP 서버 구성 | 동일 |
| 프롬프트 | 완전히 동일한 문자열 |

프롬프트는 **캐시 최소 크기를 넘겨야** 한다. 짧으면 캐시가 아예 안 생겨서 결과가 무의미하다.

### 절차

```
① 계정 A · 디렉터리 X · 새 세션
   프롬프트 P 전송
   → cache_creation_input_tokens 기록 (캐시 생성 확인)

② 계정 A · 디렉터리 X · 새 세션 (대조군)
   같은 프롬프트 P 전송
   → cache_read_input_tokens 기록
   ★ 여기서 0이 나오면 실험 설계가 잘못된 것. 계정 얘기로 넘어가면 안 된다

③ 계정 B로 전환 · 디렉터리 X · 새 세션
   같은 프롬프트 P 전송
   → cache_read_input_tokens 기록

판정: ②는 > 0, ③은 0  →  가설 지지
      ②와 ③ 모두 > 0   →  가설 기각
      ②가 0            →  실험 무효, 설계 재검토
```

②를 반드시 넣는다. 대조군 없이 ③만 보면 "캐시가 원래 안 잡히는 조건"과 구분할 수 없다.

### 측정 방법

statusline의 `current_usage` 객체, 또는 세션 중 `/usage`.

```
cache_creation_input_tokens   이번 턴에 캐시에 쓴 토큰
cache_read_input_tokens       이번 턴에 캐시에서 읽은 토큰
```

### 결과

| 단계 | cache_creation | cache_read | 비고 |
|---|---|---|---|
| ① 계정 A 1회차 | | | |
| ② 계정 A 2회차 | | | |
| ③ 계정 B | | | |

## 실험 3 — `/compact` warm vs cold 비용

상태: 미실행 · 우선순위 낮음

### 가설

캐시가 따뜻할 때의 `/compact`는 캐시가 식은 뒤보다 현저히 싸다. 요약 요청이 대화 전체를 다시 읽는데, warm이면 그 읽기가 캐시 가격이기 때문.

### 절차

동일한 크기의 대화를 두 벌 만들고, 한쪽은 작업 직후(warm), 다른 쪽은 TTL 경과 후(cold)에 `/compact` 실행. 각각의 `input_tokens`와 `cache_read_input_tokens` 비교.

**난점**: 동일 크기의 대화를 두 벌 만들기가 어렵다. 같은 세션을 두 번 쓸 수 없으므로 재현성이 낮다. 우선순위를 낮게 둔 이유.

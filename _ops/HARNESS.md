# 블로그 운영 하네스

이 블로그를 **제품처럼 운영하기 위한 구조**. 무엇을 어디에 기록하고, 어떤 진입점으로 무엇을 하고, 어떤 주기로 도는지를 정의한다.

## 설계 원칙

이 하네스는 이 블로그에 실린 [The Universal Loop](https://redlasha.github.io/software/the-universal-loop/)을 블로그 운영에 그대로 적용한 것이다.

```
관찰 ─────────→ 이해 ─────────→ 행동
 │                                │
 │   애널리틱스        전략         제작
 │   시장 조사        기획         발행
 │   글감 수집                    디자인
 └────────────── 되먹임 ───────────┘
```

그 글의 결론은 **"거의 언제나 첫 번째 단계에서 실패한다"**였다. 블로그도 같다. 대부분의 블로그 시스템은 관찰 없이 곧장 쓰기로 뛴다 — 무엇이 읽히는지, 시장에 무엇이 비었는지 모른 채 쓰고 싶은 걸 쓴다.

**그래서 이 하네스는 관찰 쪽에 의도적으로 무게를 둔다.** 7개 진입점 중 3개(research / analytics / plan)가 쓰기 전 단계다.

## 상태 — 무엇을 어디에 기록하는가

에이전트 세션은 매번 초기화된다. 하네스가 작동하려면 **판단의 근거가 파일로 남아야** 한다.

| 파일 | 담는 것 | 갱신 주체 |
|---|---|---|
| `CLAUDE.md` | 저장소 규약, 조판 규칙, 발행 절차 | 사람 (규칙이 바뀔 때) |
| `_ops/STRATEGY.md` | 목적, 포지셔닝, 독자, 성공 기준 | `/blog-plan` |
| `_ops/EDITORIAL.md` | 시리즈 계획, 발행 리듬, 다음에 쓸 것 | `/blog-plan` |
| `_ops/ANALYTICS.md` | 측정 기준, 관찰 로그, 도출한 액션 | `/blog-analytics` |
| `_ops/DESIGN.md` | 디자인 시스템, 조판·이미지 규격 | `/blog-design` |
| `_ops/DECISIONS.md` | 결정과 그 이유 (되돌릴 때 필요) | 전 스킬 |
| `_ops/research/*.md` | 조사 산출물 (날짜별, 불변) | `/blog-research` |
| `IDEAS.md` | 글감 인박스 | 아무 때나 |

**원칙 세 가지**

1. **조사는 지우지 않는다.** `_ops/research/`는 날짜별 append-only. 나중에 "그때 왜 그렇게 판단했나"를 재구성할 수 있어야 한다
2. **결정에는 이유를 남긴다.** `DECISIONS.md`가 없으면 6개월 뒤 같은 논의를 반복한다
3. **관찰과 해석을 분리한다.** `ANALYTICS.md`에 "체류시간 3분"은 관찰, "목차가 효과 있었다"는 해석. 섞으면 나중에 검증이 안 된다

`_ops/`는 Jekyll 빌드에서 제외되며 사이트에 게시되지 않는다.

## 진입점 — 7개 스킬

### 관찰

| 스킬 | 한 줄 |
|---|---|
| `/blog-research` | 시장·경쟁·주제를 조사하고 `_ops/research/`에 문서로 남긴다 |
| `/blog-analytics` | GA4·Clarity 지표를 확인하고 관찰 → 해석 → 액션으로 정리한다 |

### 이해

| 스킬 | 한 줄 |
|---|---|
| `/blog-plan` | 목적과 포지셔닝을 점검하고, 다음에 쓸 것을 정한다 |

### 행동

| 스킬 | 한 줄 |
|---|---|
| `/blog-draft` | 공식 문서 우선 리서치 → 개요 확인 → 초안 |
| `/blog-review` | 서브에이전트 팩트체크 + 구성 리뷰 |
| `/blog-publish` | 조판 검증 → 커밋 → 배포 확인 |
| `/blog-design` | 디자인 시스템 관리, 실제 렌더링 검증 |

## 루프 — 언제 도는가

| 주기 | 하는 일 | 진입점 |
|---|---|---|
| 글감이 생길 때 | `IDEAS.md`에 한 줄 | — |
| 글 하나 | draft → review → publish | 3개 스킬 |
| 격주 | 발행 1편 (짧은 글은 수시) | `/blog-plan` |
| 월 1회 | 지표 확인, 가설 검증 | `/blog-analytics` |
| 분기 1회 | 포지셔닝 재점검, 시장 재조사 | `/blog-plan` + `/blog-research` |
| 자동 (주 1회) | 링크 검사 | GitHub Actions |

## 게이트 — 무엇을 막는가

하네스의 값어치는 **하지 말아야 할 것을 막는 데** 있다.

| 게이트 | 막는 것 | 위치 |
|---|---|---|
| 개요 확인 | 방향 틀린 초안에 시간 쓰기 | `/blog-draft` |
| 서브에이전트 팩트체크 | 자기 글의 오류를 못 보는 것 | `/blog-review` |
| H1·front matter·Liquid 검사 | 제목 중복, 발췌문 오염, 빌드 실패 | `/blog-publish` |
| 배포 후 렌더링 확인 | "푸시했으니 됐겠지" | `/blog-publish` |
| 링크 검사 | 링크 부패 | Actions |

이 게이트들은 전부 **실제로 겪은 사고**에서 나왔다. 추측으로 만든 게 아니다.

## 이 하네스가 다루지 않는 것

- **글을 대신 써주지 않는다.** 판단과 경험은 사람 몫이다. 하네스는 리서치·검증·조판·배포의 반복 비용을 없앨 뿐이다
- **자동 발행하지 않는다.** 발행은 항상 사람이 승인한다
- **SNS 자동 배포는 아직 없다.** 유통은 수동 (GeekNews 공유 등)

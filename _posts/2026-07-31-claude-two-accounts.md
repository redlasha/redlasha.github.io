# 클로드 계정 두 개 쓰다가 발견한, 거짓말하는 statusline

> 관측 도구가 틀리면 그 위에서 내리는 모든 판단이 틀린다. 그리고 관측 도구는 대개 조용히 틀린다.

내 statusline은 "5시간 한도 59% 사용"이라고 표시하고 있었다. 실제로는 다른 계정 숫자였다.
그걸 모른 채 "아직 여유 있네"라고 판단하다가 두 계정이 동시에 한도에 걸렸다.

계정을 하나 더 만들고, 전환 도구를 붙이고, 그 과정에서 내가 만든 도구가 조용히 거짓말을
하고 있었다는 걸 발견하고, 결국 "5시간 한도를 어떻게 배분할 것인가"까지 다시 생각하게 된
이야기다.

**이 글에서 가져갈 만한 것 세 가지**

- 멀티 계정 환경에서 **"사용자 = 이메일"이라는 가정이 왜 깨지는지**. 같은 이메일이 여러
  조직에 속할 수 있고, 그러면 이메일로는 두 계정이 완전히 같아 보인다.
- 자격증명이 **여러 곳에 중복 저장될 때 생기는 최신성 문제**와, 비싼 조회(Keychain 접근
  팝업)를 늘리지 않고 정합성을 지키는 mtime 비교 트릭.
- 한정된 사용량을 **시간으로 쪼개는 것과 역할로 쪼개는 것**의 차이. 결론부터 말하면
  시간 분리는 대체로 헛수고다.

**등장하는 도구**

| 도구 | 무엇 |
|---|---|
| [Claude Code](https://claude.com/claude-code) | 터미널에서 돌리는 코딩 에이전트. statusline을 커스텀 명령으로 교체할 수 있다 |
| [usage-statusbar](https://github.com/redlasha/usage-statusbar) | 내가 만든 statusline. 컨텍스트 사용률, 5시간 한도, 리셋 시각, worktree 브랜치를 한 줄로 보여준다 |
| [cmux](https://github.com/manaflow-ai/cmux) | 여러 CLI 에이전트 세션을 한 창에서 관리하는 터미널 앱. 내장 브라우저와 워크스페이스 단위 세션 관리를 제공한다 |
| [claude-swap](https://github.com/realiti4/claude-swap) (`cswap`) | Claude Code 계정 전환기. 자격증명을 저장해두고 재로그인 없이 계정을 바꾼다 |

---

## 1. 시작은 statusbar였다

Claude Code는 statusline을 커스텀 명령으로 갈아끼울 수 있다. stdin으로 세션 JSON을
넘겨주면, 그걸 읽어서 한 줄을 찍어주면 된다.

내가 필요했던 건 두 가지였다.

- **컨텍스트 윈도우가 얼마나 찼는지** — stdin에 들어온다
- **5시간 사용량이 얼마나 남았는지** — `api.anthropic.com/api/oauth/usage`에서 온다

```
🧠 █░░░░12% ⏰ ███░░59% 🔄 PM5(-3h 54m)
```

왼쪽부터 컨텍스트 사용률, 5시간 한도 사용률, 그리고 다음 리셋 시각과 남은 시간이다.
작업하다 보면 어느 순간 한도에 부딪히는데, 그게 언제인지 미리 알고 싶었다.

만들어 쓰다 보니 git worktree 브랜치도 붙이게 됐다. 작업마다 worktree를 따로 파서
에이전트를 붙여두는 식으로 일하다 보면 열 개를 넘기는 건 금방이고, 그러면 지금 어느
브랜치에 있는지가 헷갈린다.

```
🌿 fix-cache-key 🧠 █░░░░12% ⏰ ███░░59% 🔄 PM5(-3h 54m)
```

## 2. 계정이 2개가 됐다

5시간 한도라는 게 있다. 한 창에서 쓸 수 있는 양이 정해져 있고, 다 쓰면 리셋될 때까지
기다려야 한다.

문제는 내 작업 패턴이었다. cmux로 세션을 십수 개 열어두고, 오래 걸리는 빌드나 대량
리팩터를 백그라운드로 돌리면서 그 사이에 리뷰나 짧은 작업을 한다. 백그라운드가 조용히
한도를 갉아먹다가, 정작 급한 걸 물어보려는 순간에 벽을 만난다.

그래서 계정을 하나 더 붙였다. 개인 org 하나, 팀(WhaTap) org 하나. **이메일은 같고 org만
다르다.**

## 3. 로그인 반복이 괴로움 → cswap

계정을 전환하려면 `/login`을 다시 해야 한다. 브라우저가 열리고, 승인하고, 돌아오고. 하루에
몇 번씩 하면 못 할 짓이다.

cswap을 쓰기 시작했다. 계정별 자격증명을 저장해두고 명령 한 줄로 전환한다.

```bash
cswap list      # 계정별 5h/7d 사용량
cswap switch 2  # 2번 계정으로
```

이걸로 로그인 문제는 끝났다. 그리고 새 문제가 시작됐다.

## 4. statusbar가 계정을 구분하지 못했다

전환을 해도 statusline 숫자가 안 바뀌는 것 같았다. 기분 탓인가 싶었는데, 어느 날 화면을
캡처해놓고 `cswap list`를 나란히 놓고 보니 명확했다.

| | 5h 사용량 | 리셋 |
|---|---|---|
| statusline이 표시한 값 | 68% | 15:00 |
| 실제 활성 계정 | 10% | 17:40 |

**활성 계정은 1번인데 statusline은 2번 숫자를 보여주고 있었다.** 5분쯤 뒤에 다시 보니
스스로 고쳐져 있었고, 거기서 원인이 잡혔다.

### 버그 ① 캐시에 계정 개념이 없었다

```ts
const CACHE_FILE = join(homedir(), ".claude", ".claude-usage-cache.json");
const CACHE_KEY  = "claude_usage";   // 계정 구분 없음. TTL 5분
```

API를 매번 때릴 수 없으니 5분 캐시를 뒀는데, 키가 하나뿐이었다. 전환해도 **캐시가 만료될
때까지 이전 계정 숫자를 그대로** 보여준다. 429를 맞으면 최대 1시간까지 늘어난다.

"전환이 반영 안 된다"가 아니라 "5분 늦게 반영된다"였다.

### 버그 ② 정본이 아니라 그림자에서 자격증명을 읽고 있었다

이건 더 고약하다. macOS에서 Claude Code의 자격증명 정본은 **Keychain**이다.
`~/.claude/.credentials.json`은 그림자 사본이고, 아예 없을 수도 있다. 그런데 내 코드는
그림자를 먼저 읽고 있었다.

```ts
return getTokenFromCredentialsFile() ?? getTokenFromKeychain();
//     ~/.claude/.credentials.json  ← 그림자가 먼저
```

문제는 이 그림자가 항상 최신이라는 보장이 없다는 것이다. 누가 언제 갱신하는지를 내가
통제하지 못한다. 실제로 cswap은 버전에 따라 다르게 동작했다. 내가 쓰던 구버전은 전환할 때
Keychain만 갱신했고, 그러면 그림자는 이전 계정 토큰을 그대로 들고 있는다. 지금 버전은
**이미 존재하는** 그림자 파일을 같은 값으로 다시 써서 mtime을 올린다(없으면 만들지는
않는다). 실행 중인 세션이 토큰을 hot-reload 하게 만들려는 의도적 설계다.

즉 내 코드는 남이 관리하는 캐시를 정본보다 먼저 믿고 있었다. 캐시 버그는 5분이면 낫지만
이건 그림자가 낡아 있는 한 낫지 않는다. 하필 예전에 "cron에서도 읽게 하자"며 Keychain 값을
그림자로 복사하는 코드를 넣어둔 적이 있었다. 그 코드가 함정을 고정시켰다.

### 버그 ③ `CLAUDE_CONFIG_DIR`을 무시했다

경로가 전부 `homedir()/.claude`로 박혀 있었다. Claude Code는 이 환경변수로 설정 디렉터리를
통째로 바꿀 수 있고, cswap도 터미널별로 다른 계정을 띄울 때 이걸 쓴다. 그 창에서는 다른
프로필을 쓰면서 기본 계정 숫자를 보여주게 된다. 아직 겪지는 않았다. 겪었다면 한참 헤맸을
것이다.

## 5. 고치기

### 계정 판별은 이메일이 아니라 organizationUuid

계정이 두 개라고 해서 이메일이 두 개인 게 아니다. **같은 이메일이 여러 org에 속할 수
있다.** 내 경우가 정확히 그렇다. 그래서 이메일로 두 계정을 구분하려 했더니, 두 계정이
완전히 같은 값으로 보였다.

유일한 판별자는 `organizationUuid`고, 이건 `~/.claude.json`에 있다.

```ts
const orgUuid = config?.oauthAccount?.organizationUuid;
```

그리고 이 파일은 cswap이 전환할 때 같이 갱신한다(로그에 `Updated config file`이 찍힌다).
덕분에 **자격증명을 건드리지 않고도** 계정이 바뀐 걸 알 수 있다.

슬롯 번호(1번/2번)는 cswap이 `~/.claude-swap-backup/sequence.json`에 들고 있어서, orgUuid로
역인덱싱해서 붙였다. cswap이 없는 환경이면 조용히 org 이름만 나온다.

```
👤1·personal   (cyan)
👤2·WhaTap     (magenta)
```

색을 다르게 준 게 생각보다 효과가 컸다. 숫자를 읽지 않아도 시야 끝에서 색이 바뀌면
전환된 걸 안다.

### 캐시는 계정별로, 단 하위호환은 남기고

캐시 키를 `claude_usage:<orgUuid>`로 쪼갰다. 전환하면 다른 파일 슬롯을 보므로 **지연 없이**
바뀐다.

다만 이 캐시 파일을 내가 만든 다른 도구(ai-usage-monitor)가 `claude_usage` 키로 읽고
있었다. 그래서 활성 계정 데이터는 기존 키에도 계속 미러링한다.

```ts
store[key] = entry;
if (key !== LEGACY_CACHE_KEY) store[LEGACY_CACHE_KEY] = entry;
```

내 도구가 내 도구의 발목을 잡는 건 개인 프로젝트의 흔한 풍경이다.

### Keychain을 정본으로, 그런데 매번은 말고

②를 고치려면 정본인 Keychain을 먼저 읽어야 한다. 그런데 그러면
`security find-generic-password`가 갱신마다 실행되고, macOS **접근 승인 팝업**이 뜬다. 한 번
"항상 허용"을 누르면 되긴 하지만, 실제로 cswap이 이 호출에서 5초 타임아웃으로 실패하는
것도 봤다. statusline이 매번 이걸 기다리게 하고 싶지 않았다.

**`.claude.json`은 전환 시 갱신된다는 사실을 그대로 썼다.** 그림자를 믿어도 되는지를
mtime 비교로 판정하면 된다.

```ts
function credentialsFileLooksStale(): boolean {
  const cred = mtimeMs(CREDENTIALS_FILE);
  if (cred === null) return true;
  const config = mtimeMs(CLAUDE_JSON);
  if (config === null) return false;
  return config > cred;   // 설정이 더 새것 = 방금 전환됨
}
```

`.claude.json`이 더 새것이면 전환이 있었다는 뜻이니 Keychain을 본다. 그리고 Keychain을
읽으면 그림자도 갱신하므로, 다음부터는 다시 그림자만 읽는다. 결과적으로 **Keychain 접근이
"전환당 1회"로 수렴한다.** 401이 오면 한 번 더 강제 조회한다.

전환 도구가 그림자를 갱신해주든 아니든 이 판정은 똑같이 동작한다. 남의 구현에 기대지
않고도 정합성이 유지된다는 게 이 방식의 핵심이다.

## 6. 그래서 5시간 한도를 어떻게 쓸 것인가

버그를 다 잡고 나니, 진짜 문제는 따로 있었다.

계정이 2개가 되고 나니 새로운 고민이 생겼다. 어느 날 **두 계정이 동시에 100%가 됐다.**
둘 다 죽으니 할 수 있는 게 없었다.

그래서 처음 떠올린 건 "**두 계정의 창을 어긋나게 하자**"였다. A 계정 창이 시작되고 2.5시간
뒤에 B 계정 창을 시작하면, 한쪽이 죽어도 다른 쪽은 절반쯤 살아 있다.

그런데 두 계정의 리셋 시각을 며칠 대조해보니, **5시간 창은 리셋 시각에 자동으로 시작되지
않는 것으로 보인다. 리셋 이후 그 계정으로 보낸 첫 요청 순간에 시작된다.** 문서로 확인한 게
아니라 관찰에서 얻은 결론이다. 그렇다면 오프셋은 오직 "언제 첫 요청을 쏘느냐"가 정한다.
놀고 있으면 그만큼 밀린다.

그럼 원하는 시각에 더미 요청 한 발을 쏴서 창을 열면 되지 않나? — 이게 내가 처음 세운
계획이었고, **틀렸다.**

**열린 창은 안 써도 시간이 흐른다. 안 쓴 몫은 리셋 때 소멸한다.** 쓸 계획 없이 창을 여는
건 그냥 손해다. 창은 실제로 작업을 시작하는 순간에만 열려야 한다.

그러면 반대로, 아예 **동시에 열면** 어떤가? 두 창이 같이 돌면 한 번에 2배를 쓸 수 있다.

계산해보면 정상 상태에서 **총량은 같다.** 교차든 동시든 5시간마다 계정 2개분이다. 다른
건 총량이 아니라 **공백의 모양**이다.

| | 동시 시작 | 2.5h 교차 |
|---|---|---|
| 순간 최대 처리량 | 2배 | 1배 |
| 최악의 공백 | 최대 5시간 전면 정지 | 완전 정지 없음 |
| 관리할 리셋 시각 | 1개 | 2개 |

동시는 "빨리 쓰고 다 같이 굶는" 구조다. 세션 십수 개가 물려 있는 상태에서 5시간 전면
정지는, 반속도로 계속 도는 것보다 확실히 나쁘다.

### 결론: 시간 분리보다 역할 분리

결국 내가 택한 건 셋 중 어느 것도 아니었다.

```
계정 2 ← 장기 백그라운드 워크트리 (빌드, 대량 리팩터)
계정 1 ← 인터랙티브 / 리뷰 / 짧은 작업
```

cswap의 세션 모드를 쓰면 **전역 계정을 안 바꾸고** 그 터미널에서만 특정 계정으로 띄울 수
있다. 디렉토리에 계정을 매핑해두면 손도 안 간다.

```bash
cswap map 2 ~/work/main-repo/.claude/worktrees   # 워크트리 전부 2번 계정
cswap map 1 ~/work/main-repo                     # 메인 레포는 1번
cswap run                                         # 매핑 따라 알아서
```

이러면 처리량은 동시 시작과 같다. 그런데 백그라운드가 폭주해 2번이 100%를 쳐도
**인터랙티브 작업은 계속 살아 있다.** 격리를 "시간"이 아니라 "용도"로 하니까 리셋 시각을
외울 필요도 없다.

시간으로 자원을 쪼개려던 문제가, 사실은 워크로드를 안 쪼갠 문제였다.

## 7. 남은 것

- 5시간만 보고 있었는데 **주간(7d) 한도와 지출 상한**이 따로 있다. 세션을 상시 십수 개
  돌리면 그쪽이 먼저 벽이 된다. 이건 계정을 늘리거나 소비를 줄이는 것 말고 방법이 없다.
  소비를 줄이는 쪽은 [따로 정리했다]({{ site.baseurl }}/software/claude-code-token-saving/) —
  캐시가 깨지는 지점을 아는 것만으로 같은 작업의 가격이 10배씩 달라진다.
- statusline은 구조상 **활성 계정 하나만** 보여준다. 두 계정을 동시에 보려면 별도
  메뉴바 앱이 낫다. 아니면 전환 도구가 캐싱해둔 파일을 읽어서 비활성 계정 숫자도 같이
  찍는 방법이 있다. 다음 버전에서 해볼 생각이다.

## 정리하며

세 가지가 기억에 남는다.

**하나.** 관측 도구가 틀리면 그 위에서 하는 모든 판단이 틀린다. 나는 statusline 숫자를
보고 "아직 여유 있네"라고 판단하고 있었는데, 그게 다른 계정 숫자였다. 100/100을 맞을
때까지 몰랐던 이유다.

**둘.** 정체성은 사람이 아니라 컨텍스트에 붙는다. 이메일이 같아도 org가 다르면 다른
계정이다. "사용자 = 이메일"이라는 가정은 대부분의 경우 맞아서, 틀릴 때 잘 안 보인다.

**셋.** 자원 부족을 시간으로 쪼개려는 충동은 대개 틀렸다. 총량이 같다면 남는 건 공백의
모양뿐이고, 그건 스케줄이 아니라 **격리**로 푸는 문제다.
